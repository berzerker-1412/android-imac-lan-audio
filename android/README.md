# LAN Audio Sender (Android)

Debug build for Android 10+; follows the sibling `../PROTOCOL.md` without protocol changes.

## Install

```sh
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

Run the iMac or MacBook receiver on the same trusted LAN. The sender keeps scanning for `_openbot-lanaudio._tcp.` receivers advertising TXT `v=1`; discovered receivers show whether each is paired, and tapping one selects it. Enter the current six-digit code and choose **Pair this Mac** to add that receiver while preserving other pairings. You may keep multiple Macs paired and select which one to use. If discovery is unavailable, enter the receiver's private IP, continue to **Pair this Mac**, then save the pairing when the receiver is discoverable or choose **Use once** to send without saving it. The phone stores each random device ID and token encrypted with Android Keystore; Android backup is disabled for the app and the credential preference is excluded from backup/transfer. Pairing does not start audio. After pairing, tap **Start sending** and approve Android's playback-capture prompt. **Stop** closes the TCP connection. Apps may block capture and produce silence.

**Unpair this phone** revokes access only on the selected Mac and clears only that encrypted phone record after the Mac confirms. If that Mac is unreachable, its saved pairing remains so you can retry. Paired receiver records remain available for selection while discovery continues.

Bonjour discovery searches for the exact saved service instance name of every paired receiver. If a receiver's private IP changes, the sender encrypts and saves its new address while preserving that receiver's device ID/token. The selected receiver shows found, not found, or address-save failure; use **Refresh selected Mac** to retry. Discovery can report a receiver found, but the receiver must be reachable to pair or unpair it.

Tap **Scan iMac QR** to scan the receiver's local pairing QR; this fills the IP and PIN only and never starts capture. Google Play services provides the scanner surface, so the app does not request direct camera permission. Bonjour advertises receiver identity/version only; output-control capability is not advertised. When a paired session starts, the sender probes `LANCTRL2` with `list_outputs`. An explicit unsupported-command response hides output selection and keeps default-output volume available; transient, malformed, or oversized list failures remain visible as refresh errors and can be retried. The app lists only outputs confirmed by the Mac, asks before changing the Mac's system default output (which affects all Mac apps), and updates route/volume only after receiver confirmation. Volume controls appear only when the active output reports readable/settable support. Bluetooth pairing/removal remains in macOS System Settings > Bluetooth.

The app can restrict playback capture to one selected launchable app by Android UID. This copies that app's eligible playback; it cannot make the selected app silent on the phone. Android's public playback-capture API offers no per-other-app mute/route control to suppress only the selected app's local sound while keeping other apps audible. Do not mute the Android media stream: the platform documents that stream volume affects all apps using that stream. Bluetooth/cast routes do not change this boundary; playback capture copies eligible app audio, while `AudioTrack` preferred-device routing applies to the capturing app's own playback track. Android source-app usage/capture policy and protected or DRM playback can prevent capture. Changing the selected app requires stopping and starting capture again with fresh MediaProjection approval. Sources: [Android playback capture](https://developer.android.com/media/platform/av-capture), [Android audio output and volume](https://developer.android.com/media/platform/output), [`AudioTrack.setPreferredDevice`](https://developer.android.com/reference/android/media/AudioTrack#setPreferredDevice(android.media.AudioDeviceInfo)).

Audio and pairing code are unencrypted. Use only a trusted LAN. The app accepts private/link-local IPs only; no hostname or public address.

## Build

```sh
./gradlew assembleDebug lintDebug
```

## Android screen flow

The sender opens on **Connect**, which shows the selected receiver, audio source, capture note, trusted-network warning, and a fixed Start action. **Change** opens **Choose a Mac** with Bonjour discovery, QR scan, private-IP entry, and fixed port 50555. Selecting an unpaired Mac or using a manual IP opens **Pair this Mac**, where the user can save a pairing or use the current six-digit code once. The audio-source picker is a full-height screen. Starting capture opens **Sending**, which keeps receiver/source status, receiver-confirmed output controls, and Stop together. Back while Connecting/Sending keeps the status and Stop action visible; the user ends the active session with **Stop sending**.

Output-management controls appear for paired sessions after a successful `list_outputs` probe, not from Bonjour capability metadata. Bluetooth devices still must be paired or removed in macOS System Settings. On resume, the Activity queries the live service and restores its current Sending/Connecting state and source/receiver summary; an idle query does not publish `Stopped` over the current screen. An API 35 emulator review covered Connect and Choose a Mac, entry into Pair this Mac, 720×1280 at 130% font scale, TalkBack service activation, and accessibility hierarchy. Sending with a reachable receiver and review on the user's phone remain pending.

## Reliability and UX work (2026-10-28)

- **Confirmed code-level failure risk:** Stop and service teardown could release `AudioRecord`, `MediaProjection`, and the socket while the worker thread was still reading or writing. Teardown now shares a resource lock, closes resources safely, and handles a concurrently running worker; repeated Start requests are ignored while a worker is alive.
- **Confirmed lifecycle gap:** Android can revoke a `MediaProjection`, but the sender did not register its stop callback. It now stops the stream and releases resources when Android ends the projection.
- **New crash target (not yet reproduced):** The report says the app exits immediately after sending starts. The service now explicitly declares the `mediaProjection` foreground-service type in `startForeground()` on Android 10+, matching its manifest declaration and Android 14+ enforcement. This is a defensive compatibility fix; without device logs, it is not confirmed as the reported crash cause.
- **Crash diagnosis:** The user reports that the app exits shortly after sending starts. The phone was not reachable for ADB, so no logcat/crash trace or physical-device reproduction could be collected; the historical root cause remains unconfirmed. Emulator discovery exposed a separate NSD callback thread crash, which was fixed and rechecked there. These code-level fixes do not prove the reported phone crash cause.
- **UX update:** Connect, Choose Mac, Pairing details, full-height app picker, and Sending are separate screens. Start is fixed on Connect; Stop is fixed on Sending. Back while the session is active keeps Sending visible so Stop remains available. Manual private-IP entry opens Pair this Mac with a **Use once** path. Emulator visual/accessibility hierarchy checks are complete for the tested surfaces; physical-device visual review remains pending.
- **Output control:** Added paired `LANCTRL2` list/select/per-output volume requests. Switching is confirmation-gated and system-wide on the Mac. Capability is determined by probing `list_outputs`; only explicit unsupported-command responses use the legacy default-volume fallback. Transient/list-size/parse failures remain retryable. No physical output was changed during verification.
- **Remote-only limit:** Android docs describe `AudioPlaybackCapture` as copying another app's playback and constrain capture by usage/UID/capture policy. Public API doesn't provide a way for this third-party app to mute or reroute another app's playback alone. Therefore one-app mode continues to play on the phone while copying eligible audio to the Mac. System media mute/volume was not used because it would affect other apps sharing the stream.
- **Verification:** `./gradlew testDebugUnitTest assembleDebug lintDebug` passed with JDK 17 (`BUILD SUCCESSFUL`, 47 Gradle tasks; 23 unit tests passed). Tests cover private-IP/manual target decisions, six-digit pair-button validation, idle/active and session-scoped lifecycle state, start during previous-worker teardown, preserving projection errors, output-list parsing/capability errors, and output-list switch-refresh/retry ordering. No phone was reachable for install/UI/audio testing.
- **Emulator review:** A temporary API 35 Google APIs arm64 AVD exposed an NSD callback crash: receiver discovery updated Android views from `ConnectivityThread`. `ReceiverDiscovery` now posts listener callbacks to the main looper and protects discovery maps across callback threads. Reinstalling the rebuilt APK and repeating receiver discovery/selection left the Activity resumed with no `CalledFromWrongThreadException` or fatal log. TalkBack enabled and bound; font scale 130% and 720×1280 layout remained readable, with scroll available. Emulator verification does not reproduce or resolve the reported physical-phone crash after Start.
